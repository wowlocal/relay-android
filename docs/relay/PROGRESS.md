  - **One WebSocket per account** (`relay-mattermost` `MattermostWebSocket`), started with the bridge (login or boot) and stopped on logout, with the library's backoff, `seq` gap handling and resume. Android network callbacks drop the socket when no network has INTERNET (the dev server behind `adb reverse` would otherwise stay reachable in airplane mode) and reconnect when one returns. Connection state goes to `ConnectionsManager.onConnectionStateChanged`: "Connecting…" while the socket is down, "Waiting for network…" without a network. "Updating…" is the client's own `getDifference`.
  - **pts and the update log** (internals §6.4): box `common` for private-chat updates, one box per megagroup. Every pts-bearing update (events, catch-up and the write path's answers) is stamped on the bridge executor and logged (`update_log`, 3 days / 2,000 per box) as `[dialog][TL bytes]`. Delivery is a `TL_updates` serialised and parsed back like a server push. `getDifference` answers the common box from the log (contiguity checked entry by entry) and adds `updateChannelTooLong{pts}` for every megagroup whose box moved since the client's date, so the client asks `getChannelDifference` for those only; that is answered from the channel's log. `differenceTooLong` / `channelDifferenceTooLong` are the fallbacks (and the answer for a chat the client does not know yet: `getChannelDifference(pts 1, limit 1)` gets the dialog and its newest message).
  - **Catch-up**: a connection that was not resumed, or the first one of a process, sets `catchUpNeeded` and makes the client call `getDifference`; the bridge first runs a REST catch-up since `sync_at` (kv, written while live; 2 min margin): per changed channel `posts?since=` (also returns deleted posts) → new posts mapped and logged as new messages, edits (and reaction changes, `update_at`) as edits, deletes as deletes, reads on another device as read updates, joined/left chats announced. More than 200 changes in one channel → that channel is reloaded (`updateChannelTooLong` + `channelDifferenceTooLong`); a gap over 2 days → `differenceTooLong`. Replaces A3's chat-list fingerprint (`needsReset`).

- **A5 done** (write path): `RelayWrite` + `RelayUploads`.
  - **Write queue**: every write is a job in one FIFO per account on the bridge executor, answered later (`RelayBridge.defer` / `DEFERRED`). Without a network nothing is tried (the message keeps its clock); transient failures (transport, 5xx, 429) keep the head job and retry with backoff up to 30 s, or at once when the socket reconnects or the network returns; later jobs wait behind it, so messages go out in order. `pending_post_id = <user id>:<random_id hex>`, and the post id is remembered per `random_id` (kv `sent:<id>`), so a retried or re-sent message is posted once; the WebSocket echo of our own post is ignored (it is mapped before the echo is handled, same executor).
  - **Answers**: `TL_updates{updateMessageID(random_id → id), updateNewMessage / updateNewChannelMessage}` stamped with the next pts of the box (the client applies them itself), edits `updateEditMessage/ChannelMessage`, deletes `messages.affectedMessages{pts, pts_count}`.
  - **Text**: `EntitiesToMarkdown` pass-through (what the user typed, as iOS; mentions by id get the username). **Reply** = thread reply: `root_id` = the target's root (a reply to a reply stays in its thread, CRT as iOS). **Edit** = `PUT /posts/{id}/patch` (text; `messages.getMessageEditData` allows own posts). **Delete** = Mattermost delete for everyone; the alert has no "delete for me" checkbox in Relay (`AlertsCreator`); a post with several files is deleted whole (the other parts follow as a live delete); a post Mattermost refuses (403, someone else's) comes back as a message with a notice. **Reactions**: Telegram's whole new set diffed against the user's reactions on the server (add / remove), answered with `updateMessageReactions`. **Forward** = Mattermost's forward: a post with the forwarded post's permalink (the server previews it); "hide sender name" (`drop_author`) copies text and files; forwards out of a DM are tagged with their dialog (`from_peer` is `inputPeerEmpty`). **Mark as unread** (chat list → More → Mark as unread) = `POST /users/me/posts/{newest}/set_unread`; "mark as read" = view.
